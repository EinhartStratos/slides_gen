# 业务反馈问题解决方案

> 来源：业务方试用反馈 6 项问题。本文逐条给出根因分析与解决方案，供评审后实施。
> 分析依据：`templete.pptx` 模板规则、`mock_ftp/` 中真实运行产物（`gen_20260903202409` 全量输入、`gen_20260907205041` 仅需求书输入）、`real_case/附件5`（评审后人工版参考答案）、`real_case/预评估.txt`（业务方"预评估结果表"样例，已确认存在但历史运行未上传）。

## 一、结论总览

| # | 业务反馈 | 根因 | 方案方向 |
|---|---------|------|---------|
| 1 | 封面字体颜色、大小不对 | 提交 `84b1e0c` 把正文字体写死后，封面标题/副标题（`type="text"`）也被套用了正文 14 磅样式；且多 run 时只还原第一个 | 写死字体只用于正文元素；封面/标题走"保格式替换"（克隆 rPr 或原位改文字） |
| 2 | 项目基本信息抓取不全 | 预处理提取任务从未提取这些字段；且字段来源不在需求书，而在《应用项目情况说明》和《工作量估算书》 | 新增文档类型识别 + 新提取任务 + 字段映射规则 |
| 3 | 需求概述多页 + 需求类别应为"业务需求" | 拆页机制存在但未生效；LLM 把章节标题"功能性需求"误填进"需求类别"列 | 修拆页阈值 + 类别取值白名单写入规则 |
| 4 | 方案要点不全、应与预评估结果强关联 | 要点取自功能点明细的接口级描述，未按需求项组织；真正的预评估表（`预评估.txt`）结构就是"需求项→涉及产品→工作说明"，但历史运行未上传 | 新增 `pre_eval` 块 + 程序化解析（合并单元格还原），方案要点按需求项逐条生成 |
| 5 | 各系统工作说明未按模板生成表格 | LLM 合并了产品行、工作量大部填"-"且总计算错 | 表格数据改由代码解析（预评估"涉及产品+版本情况+四类工作量"或工作量明细），LLM 只写改造要点 |
| 6 | 工作量及实施计划章节无法生成 | 一次运行未上传工作量表（整章被跳过，属正确行为）；批次/周期信息其实在预评估"备注"列和《情况说明》"项目开发规划"里，未路由到该页 | 预评估备注列提取批次意见 + 总工作量代码汇总；无数据则不生成（不预估） |

**用户设想的验证**：用户提出"分章节、某章节只读取对应的那一个文档"的思路是正确且可行的。当前管线 `_split_into_chunks` 已经把文档分成了 `docx/xlsx/workload/function_points/plain` 块，但分块结果在预处理后被丢弃，所有页面仍共享同一份压缩后的 `formatted_text`。方案是保留分块并做"页面→文档"路由（见第二节）。

## 二、核心机制改进：按章节路由文档上下文

### 2.1 现状

```text
requirement_text（上游合并：需求书docx + 功能点xlsx + 工作量xlsx + ...）
  → RequirementPreprocessor._split_into_chunks()  分块（提取后即丢弃）
  → _llm_extract() 12个提取任务并发              产出一篇压缩摘要 formatted_text
  → 每一页的 plan/generate 都拿同一份 formatted_text
```

问题：
- 所有页面共享同一上下文，信息密度被稀释，提取摘要丢失字段（如问题2）；
- 《应用项目情况说明》这类 docx 会被并入 `docx` 块与需求书混淆；
- `DOCUMENT_SEPARATOR_MIN_HYPHENS`（"文档名+20个横线"边界格式）配置存在但未实现，若上游不用 JSON 块格式上传，全部文本落入 `plain` 块，各提取任务输入为空 → 静默产出近乎空的摘要（高风险缺陷）。

### 2.2 方案：章节级上下文路由

1. **扩充分块类型**：`_split_into_chunks` 依据 JSON 块 `data.filename`/`data.type` 识别更多文档身份：
   - `requirement_doc`：业务需求说明书（docx）
   - `situation_doc`：应用项目情况说明（docx，文件名含"情况说明/项目情况"）
   - `workload`：工作量估算书（xlsx，沿用现有规则）
   - `function_points`：功能点估算明细（xlsx）
   - `pre_eval`：预评估结果表（xlsx，sheet 名含"预评估范围/排期意见"，或表头含"需求项,涉及产品,版本情况"）——已确认存在（`real_case/预评估.txt`）。注意现有规则 `"评估" in name → workload` 会把"预评估范围"混入 workload 块，需优先识别独立成块
   - `plain`：画图要求等其他文本
   - **输入格式兜底（已确认，必做）**：上游可能只传各文件的 content 值拼接、不保证 JSON 信封——分块必须支持**内容嗅探**：先按 JSON 信封解析（有 `data.type` 时用文件名/类型辅助）；信封缺失时按内容特征识别（`sheet-name:` 块 → xlsx；表头含"需求项,涉及产品" → pre_eval；含"工作量明细/实施部门" → workload；含"功能项编号/产品属性,FPS" → function_points；含章节标题/目录结构 → docx；其余 → plain）。识别失败整块归入 plain 并记 warning，不得静默。
2. **页面→数据源路由表**（示例，按模板页名命中）：

   | 模板页 | 主要数据源 |
   |--------|-----------|
   | 封面 / 项目基本信息 | 情况说明 + 需求书首页 + 预评估（部门/联系人列） + 工作量明细 |
   | 需求背景 / 需求简述 / 现状分析 / 假设约束 | 需求书 |
   | 需求概述 | 需求书需求提要 + 预评估"需求项"列 + 功能点明细 + 情况说明"本期需求具体情况" |
   | 项目方案概述 / 方案要点 | **预评估（需求项→涉及产品→工作说明，主数据源）** + 情况说明"功能详细介绍" + 需求书第三章功能描述 |
   | 各系统工作说明及工作量 | **预评估（涉及产品+版本情况+工作说明+四类工作量）** + 工作量明细（程序化解析） |
   | 项目总工作量 / 项目实施计划 | 工作量明细（程序化汇总） + 预评估合计行/**备注列批次意见** + 情况说明"项目开发规划" |
   | 架构图 / 主要处理流程 | 画图要求 + 需求书第二章 + 实施安排 |

3. **落地方式**：`ProcessedRequirement.chunks` 保留分块；编排层按 `page_rule.page_name` 查路由表，把命中的块原文（截断到上限）作为 `scoped_context` 追加进该页 plan/generate 的 user prompt，全局摘要仍作为兜底保留。这样每页只看到"它该看的那个文档"，与用户设想一致，且不用大改 LLM 调用链。
4. **自适应生成原则（业务已确认）**：不保证任何文档必传，**有什么做什么**——每页只依赖路由表中实际存在的块；某章所需数据源整体缺失时，按防编造规则跳过该章并**从成品中删除对应页**（不做占位、不做预估填充）。预评估为可选文档，缺失时方案要点/工作量表回退到"情况说明+工作量明细+功能点明细"链路。
5. **固定页不变量（业务已确认，最高优先级）**：**目录页与尾页固定不动**——无论输入缺失、生成失败、章节删除等任何情况，两类页面都必须原样输出（模板原文、不经 LLM 改写、不参与自适应删除）。模板目录页是固定章节结构（1.需求及现状分析 2.技术方案 3.工作量及实施计划 4.待决策事项），属样板内容；目录中列出的章节若因数据缺失被删属业务可接受结果，不为对齐目录而保留空章。现状已符合：两类页面走 `TEMPLATE_COPY_PAGE_TYPES` 原样复制通道；导出器重排/删除逻辑须把 `toc`/`end` 页标记为**不可删除**，并作为回归测试断言（成品尾页=模板尾页、目录页数=模板目录页数）。

## 三、逐条问题方案

### 问题1：封面字体颜色、大小不对

**前提**：正文字体写死（微软雅黑14磅/表格12磅）是有意设计——防止模板里斜体、绿色等"填写说明"样式污染正文，**该设计必须保留**，本问题只处理封面这类"模板样式即最终样式"的元素。

**根因**（`app/infrastructure/ppt_master/pptx_builder.py` `_set_text`，回归于提交 `84b1e0c`）：
- 该提交后 `is_body=rule["type"]=="text"` 的元素**全部**套用正文固定字体，封面标题/副标题（模板里是 `type="text"`）被误伤：实测最新导出封面标题 `sz=1400 b=0 i=0` 且无颜色，而模板本应是"微软雅黑 44磅 加粗 白色 带阴影"；副标题 16磅同样被压成 14磅；
- 次要缺陷（无论是否写死都存在）：`paragraph.text = content` 遇 `\n` 产生多个 run，只还原 `runs[0]` 的字体，后续 run 掉回默认；`title` 类型的 else 分支同样不保留颜色/阴影/东亚字体。

**方案**（写死字体仅作用于真正的正文元素，封面/标题走保格式替换）：
1. **区分元素身份**：把 `page_plan.page_type` 透传到 `StructuredPageResult.page_type`（schema 已有该字段，exporter 已在用），`fill_single_slide/_fill_slide` 据此分流：
   - `page_type=="cover"`（封面）：所有 text 元素**保格式替换**，不写死；
   - `type=="title"`（各页标题）：同样保格式（标题样式属模板设计，非说明文字）；
   - 其余 `type=="text"`（正文/说明框）：维持现状写死字体，不受模板斜体绿色干扰。
2. **保格式替换的实现**（封面与 title 共用）：清空前抓取段落 `pPr` 与首 run 的 `rPr` XML，按行重建 run 时 `deepcopy` 该 `rPr`——天然保留颜色、阴影、字体、`lang`；逐 run 应用而非只处理第一个。更稳的备选是"原位替换"：直接在现有 run 上改 `run.text`，多余 run 置空，样式零损耗。
3. **表格不受影响**：单元格样式继续走模板 `header_style/body_style`+固定字体；只需保证单元格内多 run 时每个 run 都生效。
4. **回归验证**：新增单测断言封面标题 run `sz=4400 b=1`、白色、`a:ea` 存在，副标题 `sz=1600`；再与 `附件5` 评审版封面人工比对。
5. 附带修复（顺手）：本次运行封面副标题残留了"需求编号_SP_"占位碎片，`global_page_rule_001` 可补充"文档编号中需求编号为空时删除整条占位前缀"。

### 问题2：项目基本信息数据抓取不全

**根因**：预处理 `project_info` 提取任务只向 LLM 要了"项目名称/需求编号/主办部门/版本日期"，其余字段（项目类型、项目牵头研发部门、软件中心牵头总经理室成员、软件中心项目经理）**从未被提取**；且这些信息本就不在需求书正文——分别在《应用项目情况说明》（项目类别、需求提出部门）和《工作量估算书·工作量明细》（实施部门、实施团队、产品联系人列）里。页面 LLM 在防编造规则下只能留空，行为本身没错，是"没喂到数据"。

**方案**：
- 文档路由落地后，给项目基本信息页配置数据源：情况说明 + 需求书 + 工作量明细；
- 新增/扩展提取任务，输出 `project_info` 扩展字段：
  - 项目类型 ← 情况说明"项目类别"（常规/战略/敏态/紧急）；
  - 项目牵头业务部门 ← 需求书"主办部门"或情况说明"需求提出部门"；
  - 项目牵头研发部门 ← 工作量明细"实施部门"或预评估"部门"列中主改造产品对应部门（如"开发六部"），两处冲突以工作量明细为准；
  - 软件中心项目经理 ← 主产品的"产品联系人"/预评估"联系人"列；页脚"业务联系人：张芮、韦泽恺"为业务侧联系人；
  - 业务目标/技术目标 ← 情况说明"项目整体定位及业务目标/项目技术目标"；
- 更新 `page_generation_rules.json` 的 `global_page_rule_006`：写明字段→来源映射，无来源字段允许留空。

**需业务方确认**："软件中心牵头总经理室成员"在现有输入文档中均无对应数据，需确认其权威来源（立项信息？预评估表？或允许留空/人工填）。

### 问题3：需求概述多页 + 需求类别取值

**根因**：
- 类别错填：模板第10页三张表的 `table_schema.default_cells` 已给出各自合法类别（功能性需求表→"业务需求/公共业务能力接入/业务功能整合"；非功能表→"可用性、可靠性/性能/安全生产运营/公共基础技术能力"；数据表→"业务数据需求/技术数据需求"），但 LLM 把段落标题"功能性需求"直接当成类别值填入；
- 多页未生效：拆页机制存在（`_expand_mixed_result_for_overflow` 会按布局带/表格行容量拆分并复制 slide），但 `fill_single_slide` 里 `slide_size` 被硬编码为 `{}`，溢出阈值回退成"元素最大底边"偏松；且 LLM 输出内容量不足，未触发溢出。

**方案**：
- `global_page_rule_008` 补充三类表各自的"需求类别"取值白名单，并明确"需求项按需求概述/需求项清单逐行列出"；预评估需求项名的"（功能类）"标签与"业务需求"类别做显式映射（功能类→业务需求），可同时作为需求项清单的权威来源；
- 结构化 user prompt 中对 table 元素追加提示："类别类列的取值必须从 `table_schema.default_cells` 已出现的取值中选择，禁止自拟"；
- `fill_single_slide` 传入真实 `slide_size`（`template_rules.template.slide_size.cy`），让溢出判断用真实页高；
- 结果即需求概述行数多时自动复制该页版式生成续页（与评审版"需求概述占2页"一致）；必要时可在规则中给该页加"每类需求独立成块、内容多时优先拆页"的正向指令。

### 问题4：项目方案要点不全、与预评估结果强关联

**根因**：当前要点主要由"功能点估算明细"的功能名称/功能描述生成——那是接口级描述（如"提供待处理任务列表查询接口"），业务期望的是按需求项逐条写业务级改造要点。业务所说的"预评估结果excel"已拿到样例（`real_case/预评估.txt`），其结构**本身就是按需求项组织的**，正是本问题的权威数据源——但两次历史运行均未上传该文件。

**预评估表结构**（sheet `预评估范围`，样例为财政贴息项目，6 个需求项；**行对齐语义已确认**：同一行左半的"涉及产品"由右半同位置的"主产品/部门/团队"实施，该行工作量归属其所在需求项）：
- 左半（需求范围评估）：`需求项`（合并单元格，仅每组首行有值，解析需前向填充）| `涉及产品` | `版本情况`（`有版本`=改造 / `配合测试`=仅测试）| `联系人` | `工作说明`（业务级改造要点）| `备注`（**批次排期意见**，如"可4月独立批次实施""最早可于2608批次实施"）；
- 右半（实施方+工作量）：`主产品` | `部门` | `团队` | `厂商` | 四类工作量：`开发&管控(自有)`、`开发(外购)`、`功能测试(自有)`、`功能测试(外购)`；
- 费用列（`费用合计/费用（万元）`等）：**整列忽略不用**（含 `#REF!` 坏公式，且页脚"自有人员/开发外购/测试外购"数值实为按类型汇总的总价而非单价，不可用其反推）；
- 页脚：`工作量合计`（样例 496 人天=自有255+外购241）、`业务联系人`；
- 另有 sheet `排期意见收集`（产品级批次可行性收集模板，样例中为空）和 `Sheet1`（产品清单+版本状态）；
- **上传规律（已确认）**：该表不一定每次上传，但上传时格式不变（列名/合并单元格结构稳定）。

**方案**：
- 新增 `pre_eval` chunk（识别规则见 2.2，须先于 `"评估"→workload` 命中）+ **程序化解析器**，按"行对齐"语义逐行产出：
  - `pre_eval_rows[]`：`{需求项(剥"（功能类）"后缀，注意样本存在缺右括号), 涉及产品, 版本情况, 联系人, 工作说明, 批次意见, 主产品, 部门, 团队, 开发自有, 开发外购, 测试自有, 测试外购}`——需求项按"上一非空"前向填充，同需求项多行自然聚合；
  - 聚合视图 `pre_eval_items[]`（按需求项分组）供方案要点用；`pre_eval_systems[]`（按涉及产品分组汇总工作量）供各系统工作量表用；
  - 解析容错：合并单元格前向填充、双行表头按列位置对齐、费用列整列忽略、空行/合计行单独归类；
- 方案要点页数据源切换：`pre_eval_items` 为主（需求项→工作说明→改造/配合测试产品天然齐全），《情况说明》"功能详细介绍"为补充，功能点明细降为兜底；
- `global_page_rule_014` 更新：强制"按需求项逐项输出、顺序与预评估需求项一致、数量与需求概述页一致"；内容多时依靠拆页机制自然分多页（评审版方案要点占3页）；
- 对账校验：`pre_eval_items` 的需求项集合应与工作量明细/需求概述的需求项一致，不一致记 warning 并在生成结果标注。

### 问题5：各系统工作说明及工作量未按模板出表

**根因**：表格确实生成了，但质量不达标——LLM 把 7 个配合测试产品合并成一行，自有/外员/厂商/费用列全填"-"，总计 1172 人天与估算书合计 1326 不符。这是"把确定性表格计算交给了 LLM"的典型失败，模板要求 11 列、一产品一行。

**方案**：
- **表格数据代码化**：扩展现有 `_build_product_matrix_from_workload`（已有雏形），数据源按优先级取预评估右半表或工作量明细——预评估每行即"涉及产品+版本情况+工作说明+四类工作量"，工作量明细则含实施部门/团队/联系人更全；两者同时存在时对账，不一致记 warning；
- "功能改造要点/非功能改造要点/数据需求改造要求"三列优先取预评估该产品的"工作说明"列（业务级原文），辅以情况说明功能概述（可过 LLM 精简，但行结构由代码固定：一产品一行，禁止合并）；
- 实施类型取值对齐模板惯例（新建/修改/配合测试），预评估"版本情况"列可直接映射：`有版本`→改造类、`配合测试`→仅测试，无需 LLM 判断；
- `global_page_rule_017` 更新：明确行数=产品数、列序固定、超容量自动拆页。

### 问题6：工作量及实施计划章节无法生成

**根因**（两层）：
- 最近一次运行（`gen_20260907205041`）输入只有需求书 docx、没有工作量表，所有工作量/计划页按防编造规则被正确跳过——整章缺失。需先确认业务方上传清单是否包含附件2/3及情况说明；
- 在全量输入的运行中：项目总工作量生成了但数字错误（LLM 算术不可靠）；项目实施计划被跳过，因为工作量大表和需求书里都没有"实施周期/投产批次"——该信息其实在两处：预评估`备注`列逐需求项/逐产品写了批次可行性结论（"财政贴息需求C-CAI可以于4月独立批次实施""最早可于2608批次实施""建议2606独立批次或2607常规批次"），以及《应用项目情况说明》的"项目开发规划"（实施周期、计划批次）。预评估还自带`排期意见收集`sheet（产品×批次可行性收集模板），说明该表设计上就是排期依据。

**方案**：
- 项目总工作量：代码直接汇总工作量明细或预评估合计行（自主/外员/厂商工作量、厂商费用、异地工作量），LLM 只负责写说明性文字，表格数字以解析结果为准；
- 项目实施计划：提取任务数据源扩展为 **预评估"备注"列（按需求项汇总的批次意见）+ 排期意见收集 sheet + 情况说明"项目开发规划"**，输出 `实施周期、投产批次、各批次投产需求项、无法按期实施的系统及原因`；`global_page_rule_019` 更新为按模板 10 行阶段表 + 批次说明生成，并在说明中如实反映预评估的批次分歧（哪些需求项能赶目标批次、哪些要排后续批次）；
- 无任何批次/周期数据时**不做预估、不写该页**（业务已确认：资料里没提到就不写，不按"投产时间要求"编造计划）——整章跳过；目录页为固定页原样保留（见 2.2 第5条），章节缺失不反向修改目录。

### 4.1 已确认（固化进方案）

| 事项 | 结论 |
|------|------|
| 上传清单 | 不保证用户传什么，**有什么做什么**——缺失数据源的章节直接删除（含目录条目），不做占位填充 |
| 文档合并格式 | 可能只传各文件 content 值拼接、不保证 JSON 信封——分块必须做内容嗅探兜底（见 2.2） |
| 预评估行语义 | 同一行左右对齐：**该行的任务由对应的主产品/部门实施，工作量归属所在需求项**——左右两半按行合并解析即可 |
| 预评估上传规律 | 不一定每次上传，但上传时格式不变（列名/合并单元格稳定） |
| 费用列口径 | `费用合计/费用（万元）`列**整列忽略不用**；页脚"自有人员2165/开发外购1518/测试外购1152"是按类型汇总的总价、不是单价 |

| 目录页/尾页 | **固定页**：无论任何情况都原样输出（模板原文、不删不改），优先级高于自适应删除 |

## 六、顺带发现的其他问题（未在反馈中，建议一并排查）
